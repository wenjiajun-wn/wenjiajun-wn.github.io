Ollama 基础：从本地安装到 LangChain 整合

本文介绍 Ollama 本地大模型运行环境：从定义与定位、安装配置、常用命令，到与 LangChain 的整合。

一、Ollama 简介

1.1 定义

Ollama 是一个用于在本地运行开源大模型的工具，本质是把模型下载、管理、加载、运行、暴露 API 这几件事封装起来的本地大模型运行环境。

一句话总结：

Ollama = 让你用很少的命令，在自己电脑上把开源大模型跑起来。

1.2 Ollama 解决了什么问题

如果你已经学过云端模型调用，应该知道：通过阿里百炼、DeepSeek、OpenAI 这类平台调用模型，优点是简单、稳定、开箱即用；但它也有明显局限：

  • 需要联网
  • 需要 API Key
  • 会产生调用费用
  • 某些场景下，数据不能离开本地机器或企业内网

Ollama 对应的，正好是另一条路：把模型放到你自己的电脑上跑。

因此它最直接解决的是：

  • 想离线使用模型
  • 想减少对云端 API 的依赖
  • 想做本地开发、本地测试
  • 想让敏感数据尽量不出本机
  • 想学习开源模型和本地推理的基本流程

可以把它和云端 API 调用看作两种”模型接入方式”：

  • 云端 API：模型在别人服务器上，你通过网络调用
  • Ollama 本地运行：模型在你机器上，你通过本机服务调用

1.3 Ollama 和云端 API 的区别

这里要先分清楚：很多人学习 Ollama 时会下意识地把它当成”另一个模型平台”，其实它更像是本地运行层。

维度 云端 API（如阿里百炼、DeepSeek） Ollama
模型在哪 厂商服务器上 你自己的电脑上
是否需要 API Key 通常需要 本地运行通常不需要
是否依赖联网 是 本地调用可不依赖外网，但首次拉模型一般需要联网
成本 按调用计费 模型本地推理不按 token 计费，但会消耗本机算力、内存、磁盘
适合什么 快速接入、稳定服务、无需本地硬件负担 本地开发、隐私敏感场景、离线测试、学习开源模型

从真实项目角度看，这两者不是非此即彼，而是经常配合使用：

  • 本地开发阶段，用 Ollama 跑小模型验证逻辑
  • 上线阶段，再切换到更强、更稳定的云端模型
  • 或者企业内网环境中，本地 / 私有化模型与云端模型混合使用

1.4 使用场景

从项目角度给一个比较稳的建议：

  • 本地开发 / 课程练习：适合用 Ollama
  • 企业内网原型 / 隐私敏感验证：也很适合
  • 对性能、稳定性、并发要求很高的正式推理服务：要根据业务再评估是否继续用 Ollama，还是切向更专业的推理部署方案

但也要有合理预期：

  • 它不等于”任何模型都能在你的电脑上丝滑跑起来”
  • 它也不等于”本地跑一定比云端便宜或更强”
  • 它更像一个本地推理入口，适合开发、实验、教学和一些轻中量应用

1.5 优势与局限

学习时，最好同时看到它的优点和边界。

优势：

  • 安装和使用门槛低
  • 命令简单，适合入门
  • 模型管理方便，pull / run / list / rm 一套命令就够用
  • 本地调用通常不需要 API Key
  • 与 LangChain 的 ChatOllama 集成成熟

局限：

  • 是否跑得动，强烈依赖你的机器配置
  • 模型体积大，会占内存和磁盘
  • 本地模型能力通常取决于你能跑多大的模型
  • 高并发、企业级推理服务场景，不一定优先选 Ollama

所以，对这章最准确的定位应该是：

Ollama 很适合学习本地模型、开发调试和轻量本地服务，但不是所有生产场景的唯一方案。

二、安装与配置

2.1 安装前先知道两件事

在真正安装之前，最容易忽略两件事：

  • Ollama 程序本身不大，真正占空间的是模型
  • 你未来可能会下载多个模型，因此模型目录最好一开始就想清楚

这也是为什么很多教程安装完很快就会讲 OLLAMA_MODELS。

因为模型文件一旦大起来，很容易把系统盘吃满。

2.3 运行环境与硬件预期

这里先把硬件预期说清楚，因为”能不能运行”不只是软件安装问题，更是硬件问题。

Ollama 跑得是否顺畅，主要受三件事影响：

  • 模型大小
  • 系统内存 / 显存
  • 是否有可用 GPU 加速

你可以先记一个粗略但实用的结论：

  • 模型越大，占用的内存 / 显存越高
  • 小模型更适合本地学习
  • 不是所有电脑都适合一上来就跑 14B、32B、70B 级模型

五、LangChain 整合 Ollama

5.1 从命令行到项目接入

只会用 ollama run 在终端里聊天，还不等于能把它接到自己的项目中。

真正的开发目标通常是：

  • 在 Python 代码里调用本地模型
  • 让本地模型也能接 Prompt、Parser、LCEL、Agent
  • 让本地模型和云端模型一样，进入统一的 LangChain 生态

本节的核心目的：

把 Ollama 从”命令行能聊天的工具”升级成”项目里能调用的模型端点”。

5.2 ChatOllama 是什么

ChatOllama 是 LangChain 中用于连接本地 Ollama 聊天模型的类，它负责：

  • 本地模型版本的 Chat Model 客户端

这意味着，它在使用体验上会和你前面学过的：

  • ChatOpenAI
  • init_chat_model(…)

有很多共通点：

  • 都可以 invoke()
  • 都会返回 AIMessage
  • 都能继续接 Prompt、LCEL、Agent

区别只在于：

  • 前面那些大多连接的是云端模型
  • ChatOllama 连接的是本机 Ollama 服务

可以把两条模型接入路线这样对照：

路线 模型在哪里跑 主要优点 主要限制
云端 API 服务商服务器 省本机资源、模型能力强、维护少 数据会出本机，依赖网络、额度和平台稳定性
Ollama 本机或自管服务器 控制力强、适合本地实验和私有环境 受本机显存 / 内存限制，速度和并发要自己承担

所以 Ollama 不是”取代云端模型”，而是给你多了一条本地可控的模型接入路线。

prompt基础

Prompt 基础：从提示词到模板工程

本文介绍 Prompt 基础：从提示词的定义与作用、调用入参与消息类型，到 PromptTemplate / ChatPromptTemplate 模板与外部文件加载。

一、Prompt 简介

1.1 定义

Prompt（提示词），就是你发给大模型的输入内容。

最简单的 Prompt，是一句自然语言，比如”什么是 LangChain？”；再进一步，你会给它增加角色，比如”你是一名法律顾问，请用 50 字介绍广告法”；再往后，为了让代码可复用、可维护、可协作，你会把这段输入写成模板，并把会变化的部分改成占位符。这就是从”随手提问”走向”工程化输入管理”的过程。

入门阶段可先把握一个基本判断：Prompt 不只是把一句话写漂亮，而是把模型输入组织清楚。

在真实项目中，Prompt 通常承担几件事：

  • 告诉模型它是谁，要扮演什么角色。
  • 告诉模型当前任务是什么，回答边界是什么。
  • 告诉模型输出格式应该长什么样。
  • 把用户问题、历史对话、检索结果、工具结果组合成一次完整输入。

这也是为什么随着项目复杂度提高，Prompt 会从”一个字符串”逐步演化成”多角色消息 + 模板 + 占位符 + 外部配置文件”。

1.2 Prompt 的作用

在学 LangChain 时，会把注意力都放在”接哪个模型””换哪个平台””怎么配 API Key”上，但真正到了项目里，最容易让系统效果不稳定的，往往不是模型接入，而是输入组织得不够清楚。

下面这些真实开发场景，都离不开本章内容：

  • 智能客服：需要系统提示词规定语气、身份和拒答策略。
  • 企业知识库问答：需要把”检索出来的上下文 + 用户问题”组合成一条清晰提示。
  • 多轮聊天：需要把历史对话插回当前输入，而不是每轮都从头问。
  • 结构化输出：需要提前在 Prompt 里写清楚输出格式要求，方便后面交给解析器处理。
  • 团队协作与 A/B 测试：需要把 Prompt 模板从代码里抽出来，放到 JSON / YAML 中做版本管理。

一句话：模型能力决定上限，Prompt 设计决定你能不能稳定接近这个上限。

1.3 本章代码目录

目录 作用 你会学到什么

这一章不是零散的 API 介绍，而是在回答一个问题：开发 LLM 应用时，怎样把 1-2 提示词工程基础 里学到的写法和原则，组织成一套可复用、可维护、可扩展的结构？

二、调用大模型的入参类型

先澄清一个常见的误解：很多人以为调用聊天模型时，输入永远只能是”一段字符串”。实际上，LangChain 聊天模型为了适配真实对话场景，通常支持多种输入形态。这些写法表面不同，核心都一样：把 1-2 章 里讲过的角色、任务、上下文、输入和约束，以合适的消息结构交给模型。

2.1 入参形态总览

同一次 invoke，左侧可以是多种类型的输入，中间由聊天模型处理，右侧典型返回值是 AIMessage。这也是为什么你在 第 11 章 会经常看到”正文一般通过 .content 读取”。

常见对应关系如下：

入参形态 调用时大致长什么样 适合场景
str model.invoke("请解释什么是 LangChain") 单轮、轻量、快速试接口
PromptTemplate.format(...) 后的字符串 model.invoke(prompt_str) 固定句式 + 少量变量替换
消息对象列表 model.invoke([SystemMessage(...), HumanMessage(...)]) 推荐写法，适合系统提示、多轮对话
(role, content) 元组列表 [("system", "..."), ("user", "...")] 简洁、贴近 ChatPromptTemplate 风格
{“role”: “…”, “content”: “…”} 字典列表 [{"role":"system","content":"..."}, ...] 贴近 OpenAI 风格 JSON 数据

2.2 写法一：纯字符串

最简单的输入方式，把整段说明写在一个字符串里交给模型，适合快速试接口、或单轮一句话任务。

不过在真实项目里，纯字符串也有明显局限：

  • 不方便表达系统角色与用户问题的边界
  • 不方便插入历史对话
  • 不利于后期维护和多人协作

所以，纯字符串适合起步，不适合复杂对话场景长期使用。

2.3 写法二：模板 + 占位符

如果一句 Prompt 里只有少数变量会变化，就没必要每次手写整段长文本。更合理的做法，是把固定部分写成模板，把变化部分留成占位符。

这一节本质上仍然是”字符串输入”，只是我们把字符串的生成过程工程化了。

也就是说：

  • PromptTemplate 负责生产输入
  • model.invoke(…) 负责把输入发给模型

它和 2.2 的区别不在于模型收到了不同类型，而在于我们是手写字符串，还是用模板生成字符串。

2.4 写法三：多角色消息列表

当你开始做聊天机器人、问答助手、企业知识库、代码助手时，最推荐的入参方式通常不是字符串，而是消息列表。

原因很简单：聊天模型更擅长理解”谁在说话”。把输入拆成 SystemMessage、HumanMessage、AIMessage 等不同角色，模型更容易正确理解上下文结构，而不是把所有东西都当成一大段平铺文本。

在实际项目里，这种写法特别常见：

  • 系统提示词放在 SystemMessage
  • 用户问题放在 HumanMessage
  • 历史回复可放回 AIMessage
  • 工具执行结果后续可用 ToolMessage

如果你后面要做多轮对话、Agent、RAG，这种消息列表思维会反复用到。

还有一种等价包装是 ChatPromptValue：链式编排里更常见的是由 ChatPromptTemplate.invoke(...) 得到 ChatPromptValue；下面直接构造对象，便于理解”PromptValue → to_messages() → model.invoke”的衔接。

2.5 写法四：元组列表与字典列表

除了显式使用 SystemMessage、HumanMessage 等类，LangChain 聊天模型通常还支持两种常见简写。

  • 元组列表：每项写成 (role, content)
  • 字典列表：每项写成 {"role": "...", "content": "..."}

这两种写法与消息对象列表在语义上基本等价，只是更接近手写列表或 OpenAI 风格的数据结构。

关于选择策略，可按下面的思路理解：

  • 想学得最清楚：优先用 Message 类
  • 想写得最简洁：可以用元组列表
  • 想和 OpenAI 风格请求体对齐：可以用字典列表

无论哪种方式，同步 invoke 的返回值通常仍是 AIMessage。

三、入参的消息类型

当你把输入组织成”消息列表”之后，就需要知道每种消息类型代表什么。在 LangChain 官方语境里，最核心的几类消息是：SystemMessage、HumanMessage、AIMessage、ToolMessage。

文档：英文 / 中文

3.1 四类核心消息

类型 说明 项目里最常见的用途
SystemMessage 系统消息，通常用于规定角色、风格、边界、输出格式 设定人设、回答规则、拒答策略
HumanMessage 用户消息，对应用户当前输入 放用户问题、补充条件、后续追问
AIMessage 模型回复消息 保存上一轮回复，支持多轮上下文

需要注意两个细节：

  • LangChain 的类名叫 HumanMessage，但很多平台的角色字段写的是 user：这不是冲突，而是不同层的命名习惯。你可以把它们理解成同一个角色。
  • 旧版本资料里可能会看到 FunctionMessage：在 LangChain 1.x 语境下，更常见的是 ToolMessage。如果你阅读旧教程或旧代码，看到这类差异，先把它理解为工具调用结果的旧命名即可。

  • HumanMessage 负责承载当前用户问题

例如：

  • “你是一个法律助手，只回答法律问题”
  • “输出请控制在 80 字内”
  • “如果超出范围，请明确拒答”

这些内容更适合放在 SystemMessage 里，因为它们属于”长期规则”，而不是某一轮具体问题。

这正对应了 1-2 提示词工程基础 里强调的那条原则：稳定约束和动态输入要拆开写。在 LangChain 里，这条原则最直接的落地方式就是把稳定规则放进 SystemMessage，把当前任务放进 HumanMessage。

在真实项目里，SystemMessage 往往决定：

  • 回答口吻是否专业
  • 是否允许推测
  • 是否必须引用上下文
  • 是否必须按 JSON 输出
  • 是否需要保守拒答

这也是为什么 Prompt 工程里经常会说：系统提示词是行为边界，用户提示词是当前任务。

3.3 ToolMessage 什么时候会出现

ToolMessage 不会在普通问答里频繁出现，它更常见于函数调用、工具调用、Agent 编排场景。

简单理解就是：

  1. 模型先在 AIMessage 里表达”我想调用某个工具”
  2. 代码真的去执行工具
  3. 工具结果再以 ToolMessage 的形式回传给模型

四、调用大模型的调用方式

当输入组织好之后，下一步就是把它交给模型。LangChain 聊天模型常见的调用方式有四类：普通调用、流式调用、批量调用，以及它们各自的异步版本。

这部分看起来像 API 记忆题，其实可以用一个更直观的方式理解：

  • invoke / ainvoke：一次发一条
  • stream / astream：一边生成一边返回
  • batch / abatch：一次发很多条

4.1 普通调用（invoke / ainvoke）

  • invoke：同步调用，最常用，适合单轮问答与脚本演示。
  • ainvoke：异步调用，适合异步 Web 服务、并发任务和高吞吐场景。

实际项目里怎么选：

  • 命令行脚本、教学示例、简单后台任务：优先 invoke
  • FastAPI、异步服务、并发请求：优先 ainvoke
  • 本地开源模型（Ollama 等）：实例化与端点配置见 第 12 章 Ollama 本地部署与调用，本章的 invoke / stream / batch 用法同样适用。

4.2 流式调用（stream / astream）

  • stream：同步流式输出
  • astream：异步流式输出

流式的最大价值不是”更快算完”，而是更快把正在生成的内容展示给用户。在聊天机器人、报告生成、代码生成等场景里，用户体验会明显更好。

真实项目里，stream / astream 很常用于：

  • 聊天界面的”打字机效果”
  • 长回答提前回显
  • 减少用户等待焦虑

4.3 批处理（batch / abatch）

  • batch：一次提交多条输入，统一获得多条结果
  • abatch：异步批处理

它特别适合离线任务，而不是交互式聊天。例如：

  • 批量摘要一批文档
  • 批量清洗问答数据
  • 批量评估 Prompt 效果
  • 批量为商品、评论、工单做标签分类

4.4 小结

场景 同步 异步 适合什么情况
单条调用 invoke ainvoke 单轮问答、接口服务
流式输出 stream astream 聊天 UI、长文本生成
批量处理 batch abatch 离线任务、批量评估

如果你一时记不住，也没关系，先记住这条基本规则：

先会 invoke，再学 stream，最后再补 batch 和异步版本。

五、提示词模板概览

5.1 提示词简介

在真正的项目里，Prompt 几乎不可能永远写死在代码中。原因很现实：

  • 用户问题会变
  • 角色设定会变
  • 输出要求会变
  • 业务策略会调整
  • 团队成员需要一起维护

如果每次都手写一整段 Prompt，不仅容易重复，还非常难维护。提示词模板的作用，就是把固定部分沉淀下来，把变化部分改成变量，从而让同一套提示逻辑可以反复复用。

这和 Python 的 f-string 很像：

这里的 {name} 就像 Prompt 模板里的占位符，直接把它看成”先留坑，后填值”就行。

5.2 提示词模板类型

LangChain 中常见的提示词模板主要有下面几类，本课程重点掌握前两种即可：

类型 说明 定位
PromptTemplate 面向纯文本模板，填值后通常得到一条字符串 重点掌握
ChatPromptTemplate 面向聊天模型的多角色模板，填值后得到多条消息 重点掌握
FewShotPromptTemplate 把若干”示例输入-输出”嵌入提示词 了解即可
PipelinePrompt 把多个子提示按顺序组合 了解即可

入门阶段可以先作一个简化理解：

  • 单条文本任务，先看 PromptTemplate
  • 聊天模型、多角色、多轮对话，重点看 ChatPromptTemplate

5.3 Few-shot 模板

Few-shot 的意思是：不要只告诉模型”按什么规则做”，还给它几组”输入应该怎么变成输出”的示例。

它适合下面这类场景：

  • 分类标签容易混，需要给几个标准样例
  • 输出风格有要求，单靠文字说明不够稳
  • 任务规则不复杂，但希望模型模仿固定格式

入门阶段不用急着背 FewShotPromptTemplate 的所有参数，先记住一句话：Few-shot 是把示例变成提示词的一部分，让模型照着样子做。等你后面做分类、抽取、客服话术生成时，再把它作为提高稳定性的手段即可。

六、文本提示词模板（PromptTemplate）

6.1 简介

PromptTemplate 是 LangChain 中最基础的模板类，适合把一段文本 Prompt 做成”固定骨架 + 动态变量”的形式。

它最适合的场景是：

  • 摘要、改写、翻译、分类等单轮文本任务
  • 还不需要明确区分 system / user 角色
  • 需要频繁替换少量变量

如果你把它和第 2 节联系起来看，会更容易理解：PromptTemplate 的结果通常还是字符串，只不过这条字符串不再靠手写，而是由模板生成。

6.2 常用参数

参数 说明
template 模板字符串，内部可包含 {变量名} 占位符
input_variables 调用时需要传入的变量名列表
partial_variables 在模板创建阶段就预先固定的一部分变量

其中，partial_variables 尤其值得理解。它的作用很直接：

把那些”经常不变”的变量先固定住，后续每次只传真正会变化的部分。

典型例子：

  • 系统角色长期固定为”Python 工程师”
  • 但用户问题每次都不同

这样一来，你就不用每次都重复传 role="Python 工程师"。

6.3 常用方法

方法 返回值 适合场景 案例源码
format(…) str 最常用，拿到字符串后直接给模型或自己继续拼接 PromptTemplate_FormatMethod.py
invoke({…}) PromptValue 需要接入 LangChain 链时更自然 PromptTemplate_InvokeMethod.py
partial(…) 新的 PromptTemplate 先固定部分变量，再多次复用 PromptTemplate_PartialMethod.py

实用建议是：

  • 刚入门时优先用 format
  • 做 LCEL 或链式调用时再逐渐理解 invoke
  • 同一模板长期复用时再考虑 partial

6.4 创建方式

PromptTemplate 常见有两种创建方式：

  • 构造函数：手动指定 template 和 input_variables
  • **from_template(…)**：由 LangChain 自动推断变量名

从经验上看，可按下面的方式选择：

  • 模板简单：优先 from_template(…)
  • 你想显式表达变量名：用构造函数

除了创建方式，本章还保留了两个补充案例。

第一，组合多个模板：当一个 Prompt 由多个子部分拼起来时，可以通过 + 组合模板，而不是手写超长字符串。真实项目里，这在”角色说明 + 业务规则 + 当前任务”这种分段组织里很有用。

**第二，比较 partial_variables 与 partial()**：二者都能做到”先固定一部分变量，后续只传剩余变量”，但一个发生在模板创建阶段，一个发生在已有模板基础上。

七、对话提示词模板（ChatPromptTemplate）

7.1 简介

如果说 PromptTemplate 更适合”单条文本输入”，那么 ChatPromptTemplate 就是为”聊天模型场景”准备的模板类。

它比 PromptTemplate 更贴合真实项目，因为真实聊天应用往往不只是”一句话”，而是：

  • 一条系统设定
  • 一条或多条用户消息
  • 可能还有历史 AI 回复
  • 可能再插入工具结果或历史上下文

这时，把所有内容写成一大段纯文本虽然也能跑，但不如把它们拆成带角色的消息来得清晰。

所以你可以把 ChatPromptTemplate 简单理解成：”面向多角色消息的模板系统”。

7.2 常用参数

ChatPromptTemplate 的核心不是单个 template 字符串，而是一组”消息模板”。每一项都可以是下面这些形式：

类型 说明 案例源码
元组 ("system", "你是{name}") ChatPromptTemplate_TupleParam.py
字典 {"role": "system", "content": "你是{name}"} ChatPromptTemplate_DictParam.py
Message 类 SystemMessage(content="你是{name}") ChatPromptTemplate_MessageParam.py
MessagesPlaceholder 在模板中预留一段”消息列表占位” 见 7.5 节

三种常规写法里，没有绝对的谁对谁错，可以按下面的经验来选：

  • 元组：最简洁，教学和业务代码里都很常见
  • 字典：更贴近 OpenAI 风格 JSON，方便和网关数据结构对齐
  • Message 类：最显式，角色最清楚，适合教学和复杂场景

下面这个基础示例能帮助你直观看懂三种写法的共同点：它们都是在定义”系统说什么、用户说什么、哪些部分由运行时填值”。

7.3 常用方法

方法 返回值 使用建议
format_messages(…) List[BaseMessage] 最直观，得到消息列表后交给模型
invoke({…}) ChatPromptValue 适合与 LangChain 链条衔接，也可直接交给模型
format(…) str 适合查看最终拼接效果，不推荐作为聊天主写法

这三个方法最容易混淆，建议这样理解：

  • format_messages：我要的是”消息列表”
  • invoke：我要的是”PromptValue 对象”
  • format：我要的是”纯字符串”

对实际项目来说，建议优先采用这两种：

  • format_messages(...) -> model.invoke(messages)
  • invoke({...}) -> model.invoke(prompt_value)

因为这两种方式都能保留清晰的消息角色结构。

7.4 创建方式

ChatPromptTemplate 常见也有两种创建方式：

  • ChatPromptTemplate.from_messages([...])
  • ChatPromptTemplate([...])

它们的核心差别不大，本质上都是把一组消息模板交给 ChatPromptTemplate。

经验上更推荐优先使用 from_messages(…)，因为可读性更好，也更符合官方文档和社区示例的主流写法。

7.5 MessagesPlaceholder

MessagesPlaceholder（消息占位符）这是本章最重要的知识点之一，很多人一开始会觉得它抽象，但一旦理解，就会发现它几乎是多轮对话、记忆、历史上下文拼接的关键。

先说结论：MessagesPlaceholder 的作用，就是在模板里先留出一段”消息列表的位置”，等真正调用时再把历史对话整块塞进去。

如果没有占位符，你就只能在代码里手动拼接 HumanMessage、AIMessage，又乱又难维护。

它常见有两种写法：

  • 显式写法：MessagesPlaceholder("memory")
  • 隐式写法：("placeholder", "{memory}")

二者的核心思想完全一样，只是语法风格不同。

典型结构通常是：

  • 系统设定
  • 历史消息占位
  • 当前用户问题

这段代码的价值在于，它让模板本身变得非常稳定，而把”历史有几轮、具体内容是什么”延迟到运行时再决定。

八、从文件加载提示词

当 Prompt 还很短时，把它直接写在 Python 代码里问题不大；但只要你开始做真实项目，就会很快遇到几个问题：

  • Prompt 越来越长，代码越来越乱
  • 产品、运营、算法同学希望一起改 Prompt
  • 需要保留多个版本做 A/B 测试
  • 想把 Prompt 与代码逻辑分离

这时候，把 Prompt 放到 JSON / YAML 等外部文件中，就会更工程化。LangChain 提供了 load_prompt(...)，可以根据文件内容加载为模板对象。对于本章案例来说，最常见的是 _type: "prompt"，即加载为 PromptTemplate。

大模型基础第一章

大模型基础（一）：认识大模型

本文是”大模型基础”系列的第一章，从定义、由来、计量单位、分类方式到开源与闭源，带你建立对大模型的整体认知。

1.1 定义

目前对大模型（Large Models）并没有绝对统一的严格定义，但在教学层面上，通常指的是：

  • 参数规模大
  • 训练数据多
  • 训练算力强
  • 能够在多种任务上表现出较强通用能力

很多资料会把”参数量达到 10 亿以上”作为一个粗略分界线。这个分界并不是一条严格法律线，但它有助于建立一个直观印象：

大模型 = 用海量数据和强算力训练出来的超大规模深度神经网络模型。

其次，有一个常见的混淆：

  • 模型：是底层能力的本体，比如 Qwen、DeepSeek、GPT 等这类模型
  • 产品：是对外提供给用户使用的完整系统，比如 ChatGPT、Claude、DeepSeek Chat、Qwen Chat、各种 AI 助手和智能体平台

还有 BERT 和 BART：

  • BERT：Google 开发
  • BART：Meta（原 Facebook）开发

它们都属于 NLP 时代的重要模型，但通常不归入今天常说的”大模型主流范畴”，更适合被理解为”大模型之前的重要阶段性代表”。

NLP（自然语言处理）：让计算机理解和生成人类语言。

1.2 为什么会出现大模型

大模型的出现，是数据规模、计算能力、模型架构三方面共同演进的结果。

1.2.1 数据够多

训练范式的变化，让模型能够使用的训练数据规模发生了数量级提升。

什么叫”训练范式”？

可以把”范式”看作某一类问题的标准做法、主流做法、常用方法框架。放到这里，训练范式指的就是”模型通常按照什么思路、用什么类型的数据、完成什么训练任务来学习”。

例如：

  • 传统监督学习范式：依赖人工标注数据，让模型学习”输入 → 正确答案”
  • 自监督学习范式：不依赖人工标注，而是让模型从数据本身构造学习任务，比如”预测下一个 token”

放到训练里看，范式不是某一个具体算法，而是一整套训练思路。

传统机器学习和早期深度学习通常更依赖人工标注数据，而大模型时代最关键的变化是：大量模型采用了自监督学习范式，例如”预测下一个 token””根据上下文恢复被遮住的部分”等。

更直白地说：以前是”人先把答案标出来，再教机器”；现在更多是”机器从数据本身的结构里自己找学习信号”。

1.2.2 算力够强

深度学习训练本质上是大规模矩阵运算，而矩阵运算天然适合并行计算。GPU、TPU、NPU 这类芯片的发展，让这种计算终于变得现实。

  • TPU（Tensor Processing Unit，张量处理单元）：可以看作是为云端大规模 AI 模型打造的”算力巨兽”。
  • NPU（Neural Processing Unit，神经处理单元）：可以看作是专为终端设备 AI 任务设计的”节能专家”。

今天训练超大模型时，常见的并行方式包括：

  • 数据并行：不同设备处理不同数据批次（每个设备持有完整的模型副本，不同设备处理不同的数据子集，通过梯度聚合同步更新模型参数）
  • 张量并行：把同一个大矩阵切到不同设备（将模型中的张量（如权重矩阵）按维度切分到不同设备上，每个设备只处理部分张量，通过集合通信合并结果）
  • 流水线并行：把模型不同层分配到不同设备（将模型按层或模块切分成多个阶段，每个阶段分配到不同设备，数据按流水线方式依次传递）

大模型不是”某一张卡突然特别强”，而是硬件 + 集群 + 并行训练方法一起推动起来的。

1.2.3 架构合理

Transformer 架构是大模型时代最关键的技术转折之一。它的重要性不只是”效果好”，更在于它具备很强的可扩展性。

“可扩展性”可以简单理解为：当你继续增加模型规模、训练数据和训练算力时，模型性能往往还能继续提升，而不是很快碰到天花板。

Transformer 能把”更多参数 + 更多数据 + 更多算力”比较稳定地转化成更好的模型性能。因此，”大模型时代”会建立在 Transformer 架构之上：只有架构本身能继续吃下数据和算力，持续堆叠才有价值。

1.2.4 架构演进

Transformer 是沿着 NLP 架构演进走出来的。它逐步解决了早期模型在长文本、并行训练和信息传递上的问题。

从 RNN 到 Transformer，可以先抓住这条主线：

阶段 核心思路 主要问题
RNN 按顺序一个词一个词读，前面的状态传给后面 长文本容易遗忘，训练难并行
LSTM / GRU 在 RNN 基础上加入门控机制，尽量保留重要信息 缓解长期依赖，但仍然偏串行
Seq2Seq 用编码器读输入，用解码器生成输出 中间向量容易成为信息瓶颈
Seq2Seq + Attention 解码时动态关注输入中的不同位置 仍然保留 RNN 的串行包袱
Transformer 用注意力机制直接建模任意 token 之间的关系 更适合并行训练和规模扩展

RNN 的工作方式很像”按队伍顺序传话”：第 10 个词想理解第 1 个词的信息，需要一层层传过来。句子短时还能工作，序列一长，早期信息就容易被冲淡。

所以，Transformer 的意义可以概括成三点：

  1. 并行计算：不再必须一个词等一个词地顺序处理，更适合 GPU 集群训练。
  2. 全局依赖：任意两个 token 可以通过注意力直接建立关系，更适合长距离信息建模。
  3. 可扩展性：模型、数据和计算量继续扩大时，效果通常还能稳定提升。

1.2.5 Decoder-Only

Transformer 本身包含编码器和解码器，但后来形成了三条常见技术路线：

架构路线 典型用途 直观理解
Encoder-Only 表征、分类、检索、Embedding 更擅长”理解输入”
Encoder-Decoder 翻译、摘要等输入输出边界清晰的任务 先读懂输入，再生成输出
Decoder-Only 对话、写作、代码生成、通用生成 给定上下文，不断预测下一个 token

现代通用 LLM 基本采用 Decoder-Only，核心原因是它天然适合”自回归生成”：

  1. 先把输入文本切成 token，并映射成向量。
  2. 模型根据已有上下文预测下一个 token 的概率分布。
  3. 采样或选择出下一个 token。
  4. 把新 token 追加到上下文后面，继续预测下一个。

你给模型的 System Prompt、用户问题、历史消息、检索结果、工具返回，最后都会变成 Decoder-Only 模型继续预测下一个 token 的上下文。

1.2.6 小结

大模型之所以会出现，核心原因可以总结成三句话：

  1. 数据规模上来了
  2. 算力基础设施跟上了
  3. Transformer 架构让扩展变得有效了

三者叠加，才真正迎来了今天的大模型时代。

1.3 大模型计量单位

理解大模型时，最常见的三个尺度是：

  • 参数规模
  • 训练数据规模
  • 计算规模

1.3.1 参数规模

常见误区：模型参数不是”层数、神经元数量、超参数”的统称。更准确地说，参数主要指模型里通过训练学出来的权重（weights）和偏置（biases）。

所以当我们说一个模型是 7B、70B 参数时，通常指的是模型里这类可训练数值的总量很大，而不是单纯指”层数多”或者”神经元多”。

大模型参数规模（Parameters Scale）常用 B 表示，即 Billion，10 亿。例如：7B = 70 亿参数，70B = 700 亿参数。

参数越多，通常意味着模型能表示更复杂的模式，但并不代表”一定更强”。效果还取决于训练数据质量、训练策略、架构设计和推理方式。

1.3.2 训练数据集规模

大语言模型的训练数据规模，通常用 token 数量来衡量。

这里要特别理解 token 不是”字数”，也不是”单词数”的简单等价。

token 是模型处理语言时的基本切分单位。对中文来说，一个汉字可能是一个 token，也可能不是；对英文来说，一个单词可能是一个 token，也可能被拆成多个 token。

所以你会在大模型领域经常看到：

  • 上下文长度是多少 token
  • 训练数据是多少 token
  • 输入消耗了多少 token

如果你想更直观地体验，可以直接用 OpenAI 的 Tokenizer 工具测试：https://platform.openai.com/tokenizer

1.3.3 计算规模

模型训练要消耗大量浮点运算，因此常用 FLOPs（Floating Point Operations）来衡量计算规模。

  • 1 FLOP = 1 次浮点运算
  • 1 PFLOPs = 10¹⁵ 次浮点运算
  • 1 EFLOPs = 10¹⁸ 次浮点运算

不必死背单位换算，但要知道：训练大模型不是”数据喂进去就完了”，而是要为海量数据和巨大算力付出极高的工程与资金成本。

1.4 大模型分类

大模型常见的两种分类方式是：

  • 按模态分类
  • 按功能 / 输出形态分类
分类标准 类别 示例
按照模态分类 大语言模型（LLM） Qwen / DeepSeek / GPT / Claude
多模态理解模型（Multimodal Understanding） GPT-4o / Gemini / Qwen-VL
多模态生成模型（Multimodal Generation） Stable Diffusion / DALL·E / Sora
按照功能分类 大语言模型 / 生成模型（LLM） GPT / DeepSeek / Qwen
嵌入模型（Embedding） BGE / E5 / GTE
重排序模型（Reranker） BGE-Reranker / Cross-Encoder 系列
分类模型（Classifier） 各类经过微调的文本/图像分类模型

1.4.1 根据模态分类

根据模态，可以把大模型分为：

  • 语言大模型（LLM）
  • 多模态理解模型
  • 多模态生成模型

什么是模态（Modality）？
模态指的是机器感知和处理世界的不同信息形式，例如：文本、图像、音频 / 语音、视频等。

类型 1：语言大模型（Large Language Model，LLM）

又称语言 / 文本大模型，专门处理文本序列。

类型 2：多模态理解大模型

能够同时处理文本和图像、音频、视频等多种模态，并通常输出文本结果。

类型 3：多模态生成模型

不仅能理解多模态输入，还能生成图像、视频、音频等内容。

注意：ChatGPT、Claude、Gemini 这类面向用户的产品，往往不只是单一模型，而是一个以模型为核心、再叠加工具、多模态输入输出、记忆和产品能力的系统。

1.4.2 按模型功能 / 输出形态分类

按功能和输出形态来分，可以分成四类：大语言模型 / 生成模型（LLM）、嵌入模型（Embedding Model）、重排序模型（Reranker）、分类模型（Classifier）。

类型 1：大语言模型 / 生成模型（LLM）

这里说的”生成模型”，指的是负责根据上下文生成文本结果的 LLM。对话模型可以理解为 LLM 在聊天场景中的一种常见使用形态，但不能把所有 LLM 都简单等同为对话模型。特点：

  • 输出：token 序列
  • 目标：预测下一个 token
  • 典型应用：对话、写作、RAG 最终回答、代码生成、Agent 决策

类型 2：嵌入模型（Embedding Model）

嵌入模型不负责生成文本，而是把文本或图像映射为向量表示。特点：

  • 输出：固定维度向量
  • 典型应用：语义搜索、推荐、知识库检索、相似度计算

类型 3：重排序模型（Reranker）

重排序模型会对初步检索到的候选结果重新打分和排序。特点：

  • 输入：(query, doc)
  • 输出：相关性得分
  • 典型应用：RAG 检索结果精排、搜索排序优化

类型 4：分类模型（Classifier）

分类模型负责把输入归到预定义类别里。特点：

  • 输出：标签 / 概率 / 是非判断
  • 典型应用：情感分析、意图分类、垃圾内容识别、主题分类

四者关系对比：

维度 大语言模型 / 生成模型（LLM） 嵌入模型（Embedding） 重排序模型（Reranker） 分类模型（Classifier）
核心任务 内容生成 语义编码 相关性排序 类别预测
输出形式 自然语言 / 多模态 高维向量 相关性分数 类别标签
典型位置 最终回答 / 决策 检索前处理 检索后精排 过滤 / 路由 / 标注

协同工作流程

在实际项目里，这四类模型经常一起工作：

  1. 用 Embedding 把文档转成向量并存入向量库
  2. 用户提问时，用 Embedding 把问题也转成向量
  3. 先检索候选文档
  4. 用 Reranker 做精排
  5. 必要时用 Classifier 做过滤或意图判断
  6. 最终把结果交给 LLM 生成回答

这正是很多 RAG 系统的典型结构。

具象理解：四类模型如何配合（以知识库 + 硅基流动为例）

大家平时接触最多的是聊天产品里的对话形态：你问一句，它答一句。但在工程实现里，真正负责生成回答的通常称为大语言模型或生成模型。当你开始做知识库、RAG 或问数系统时，往往还会同时接触嵌入模型、重排序模型和分类模型。

以”你在硅基流动选模型、在 Cherry Studio 等工具里建知识库”为例，可以按这个方式理解：

  1. 大语言模型 / 生成模型（LLM）
    • 负责最后生成自然语言答案
    • 是用户最直观看到的”大模型”
  2. 嵌入模型（Embedding）
    • 负责把文本变成向量
    • 是知识库检索的基础
    • 建库和查询时必须使用同一类嵌入模型或同一向量空间
  3. 重排序模型（Reranker）
    • 负责对召回候选结果重新打分
    • 作用是让最相关的几条排到更前面
  4. 分类模型（Classifier）
    • 负责给问题或候选文档打标签
    • 可用于意图判断、过滤无关结果、选择路由

一条用户提问在系统里的顺序通常是：

  1. 用户提问
  2. （可选）分类模型判断意图
  3. 嵌入模型做向量检索
  4. （可选）重排序模型精排
  5. （可选）分类模型继续过滤
  6. LLM 生成最终答案

1.5 大模型的开源 vs 闭源

1.5.1 大模型四要素

一个大模型通常可以拆成四个关键要素：

  • 模型权重（参数）
  • 推理代码
  • 训练代码
  • 训练数据集

其中，训练代码基本不开源；训练数据集属于大厂的核心竞争力（大厂可能会花钱购买数据并进行人工标注），通常也不会开源；而模型权重（参数）是开放的，可以部署到自己的服务器上。

1.5.2 开源 vs 闭源大模型

开源 / 开放权重大模型：不同于传统软件的开源，大模型开源多数时候指开放权重（模型参数），可能包含推理代码、模型配置、Tokenizer 和使用示例，但通常不包含完整训练代码和训练数据集。能否商用、能否再分发，还要看具体许可证。

  • 典型代表：DeepSeek 系列、Qwen 系列、Llama 系列、文心大模型 4.5

闭源大模型：特定企业开发并保密，源代码和内部实现不对外公开。

  • 典型代表：GPT 系列（不包括早期的 GPT-1、GPT-2，以及最近开源的 GPT-OSS 系列）、Gemini 系列（大多数）、Claude 系列

开源 vs 闭源对比：

维度 开源大模型 闭源大模型
透明度 代码和算法完全透明，可审查验证 内部机制不透明，存在”黑箱”问题
可访问性 免费使用，降低技术门槛 需要特定许可或授权，通常付费
定制性 支持深度定制和优化 定制能力受限，仅限 API 参数调整
创新速度 社区协作推动快速迭代 依赖单一团队，创新速度较慢
成本结构 免费使用，但需硬件和运维投入 按使用量付费，前期投入低但长期成本高
技术支持 依赖社区，缺乏官方专业支持 提供企业级技术支持和维护服务
安全性 透明可审计，但可能被恶意利用 代码不公开，保护知识产权和用户数据

AWS云技术与服务概念

AWS 云技术：从计算、存储到 AI

云计算的世界很大，AWS 提供的服务也很多。想在短时间内学习 AWS 核心服务的整体认知，从计算、数据库、网络存储，一路到 AI/ML，是一条很实用的学习路径。

一、计算服务：从 EC2 到无服务器

EC2：云上最基础的计算单元

Amazon EC2（Elastic Compute Cloud）提供的是可伸缩的云端计算能力，每一台虚拟机被称为一个”实例”。它的核心特点是可以根据需求灵活地扩容或缩容，并且提供多种针对不同场景优化的实例类型。AWS 把 EC2 实例分成六大类：

  • 通用型：兼顾计算、内存与网络资源的均衡配置，适合动态网站、代码仓库等场景。
  • 计算优化型：面向计算密集型的高性能工作负载，比如科学模拟、金融建模。
  • 内存优化型：适合内存消耗大但存储需求不高的场景，比如实时流数据分析、字幕生成。
  • 存储优化型：擅长对大数据集进行高吞吐的顺序读写，常用于数据仓库、大型关系型数据库重构。
  • 加速计算型：搭载 GPU、FPGA 等专用硬件加速器，适合深度学习、游戏图形渲染。
  • 高性能计算（HPC）优化型：在大规模高性能工作负载上追求最佳性价比，用于天气预测、碰撞模拟等场景。

连接 EC2 实例的方式也有好几种：通过 SSH 客户端用密钥连接（需要自行管理密钥）、通过 AWS Session Manager 实现无密钥的、与 IAM 集成的访问，或者用 EC2 Instance Connect 做基于浏览器的临时快速连接。

负载均衡与自动扩缩容

当流量增大时，靠一台实例显然扛不住。负载均衡的作用是把进来的请求均匀分配到多个 EC2 实例上，避免单点过载，同时保证高可用性和水平扩展能力。它的工作流程是：用户请求先到达负载均衡器，负载均衡器优先把流量导向主目标组；如果需求继续上升，再激活备用目标组，把负载分散到所有实例上。

弹性（Elasticity）则是指系统能够根据需求自动伸缩资源的能力，这在 EC2 上是通过 Auto Scaling 实现的：系统会根据实际使用情况自动增减活跃实例数量，从而优化成本、避免资源过度配置。简单说，负载均衡负责”把流量分匀”，自动扩缩容负责”按需增减机器”——二者经常配合使用，但解决的是不同的问题。

容器与无服务器计算

随着微服务架构和事件驱动应用的普及，传统的常驻计算模式已经不够用了。容器把应用程序及其依赖打包成轻量的独立单元，既能与底层系统解耦，又能共享宿主操作系统资源，还便于跨环境迁移。AWS 提供两个主要的容器服务：

  • Amazon ECS：全托管的容器编排服务，适合部署和管理微服务应用，也能用来做批处理任务的调度和运行。
  • Amazon EKS：专注于运行基于 Kubernetes 的容器编排服务，常与加速计算型 EC2 实例搭配运行机器学习容器，也适合管理混合云环境下的集群。

而无服务器架构则更进一步：完全不需要管理服务器，由事件触发函数执行，并且只为实际用量付费。AWS Lambda 是这一领域的代表，可以在响应事件时自动运行代码并弹性伸缩计算资源。AWS Fargate 则为容器提供无服务器化的运行环境，常用于无需大量服务器预置的 AI/ML 应用，以及需要并行处理能力的大规模批处理任务。

二、数据库、网络与存储：AWS 的数据基础

数据库服务

AWS 的数据库服务让用户无需自建物理基础设施或安装软件就能直接使用数据库。按数据模型划分，主要有三类：

关系型数据库将数据组织成带有预定义关系的表结构，优势在于数据完整性、一致性与可扩展性。AWS 在这方面提供：

  • Amazon RDS：全托管关系型数据库服务，支持多种数据库引擎，可高效扩展云端及本地数据库。
  • AWS Aurora：针对 MySQL 和 PostgreSQL 优化的关系型数据库，性能出众且成本仅为传统方案的约十分之一，内置持续备份和跨区域自动复制。

NoSQL 数据库用于处理 JSON、文档等超出传统关系模型的多样化数据，具备模式灵活性和水平扩展能力。代表服务是 Amazon DynamoDB——一款无服务器、全托管的 NoSQL 数据库，能在任意规模下实现个位数毫秒级的响应性能，可用吞吐几乎不受限，并提供 99.999% 的全球可用性，常用于实时视频流媒体、购物车追踪、游戏玩家数据和排行榜等场景。此外，Amazon DocumentDB 是兼容 MongoDB 的原生 JSON 文档数据库，适合内容管理系统、用户画像管理，乃至语义搜索、产品推荐、聊天机器人等生成式 AI 场景。

内存数据库利用 RAM 实现高性能的数据存取，适合缓存高频访问数据、实时分析和高速事务处理。MemoryDB for Redis 就是 AWS 在这一领域的方案，具备超高速读写、99.99% 可用性以及近乎零数据丢失的快速恢复能力。

值得一提的是，除了这些全托管方案，用户也可以选择在 EC2 实例上自行部署数据库，这种方式能提供更细粒度的配置控制，但备份和补丁维护的责任也完全落在用户自己身上。

数据库迁移

面对遗留系统难以满足快速扩展需求，以及生成式 AI 对算力和存储提出的更高要求，数据迁移成为许多企业绕不开的课题。AWS 提供了一套迁移工具组合：

  • AWS Database Migration Service：支持 20 多种数据库和分析引擎的迁移，通过自动化实时数据复制将停机时间降到最低，并提供校验检查和任务监控。
  • AWS Snow Family：提供物理设备，用于 PB 级数据的离线传输，适合边缘场景下的大规模数据搬迁。
  • AWS DataSync：通过并行处理简化、自动化并加速本地存储与 AWS 云之间的大数据量传输。
  • AWS Schema Conversion Tool：自动将源数据库的模式转换为目标格式，支持自定义转换规则，并提供诊断与优化建议。

网络服务

Amazon VPC（Virtual Private Cloud）是 AWS 云中一个逻辑隔离的网络空间，用户可以在其中启动和管理自己的资源。它支持 IPv4 和 IPv6、可自定义 IP 地址范围，并通过安全组和网络访问控制列表（ACL）提供多层安全防护，同时允许用户完全掌控子网、路由表和网关配置。AWS 会自动创建一个默认 VPC（带有预配置的子网和默认联网能力），用户也可以创建完全自定义的 VPC。

在网络安全层面，网络 ACL 相当于子网级别的防火墙，安全组则是实例级别的防火墙。而 VPC 终端节点和 AWS PrivateLink 能够让 AWS 服务之间、乃至与本地网络之间实现私有连接，无需暴露公网 IP。至于连接本地网络与云端的方式，AWS VPN 适合小规模或临时性连接场景，AWS Direct Connect 则提供专线连接，拥有更高带宽和更低延迟，适合关键业务的持续性负载。

此外，Amazon Route 53 作为 DNS 服务负责把域名解析为 IP 地址，而 Amazon CloudFront 作为内容分发网络（CDN），通过在全球部署缓存节点来加速网页内容、API 与流媒体的传输，同时提供 DDoS 防护和 HTTPS 支持。

存储解决方案

AWS 的存储服务大致可以分为四类：

  • 对象存储：以”对象”为单位管理非结构化数据，支持水平扩展和元数据管理。Amazon S3 是这一领域的旗舰产品，提供 99.999999999%（11 个 9）的数据持久性，并覆盖所有 AWS 区域。S3 还细分出多种存储类别：Standard（高频访问）、Intelligent-Tiering（自动根据访问模式切换层级以优化成本）、One Zone-IA（单可用区、低成本，适合易于重建的低频数据）、Glacier（低成本归档，检索时间从几分钟到几小时不等）、Glacier Deep Archive（最低成本、检索时间最长）以及 S3 Outposts（本地存储延伸，打通私有云与公有云数据）。
  • 块存储：把数据切分成带有唯一地址的固定大小数据块，适合高 I/O 事务型应用和大数据分析引擎。Amazon EBS 是专为配合 AWS 计算服务设计的高性能块存储方案。
  • 文件存储：以分层结构组织数据，支持多用户多服务的并发读写。Amazon EFS 适用于简化 DevOps 流程、增强内容管理系统性能，以及加速数据科学工作。
  • 缓存存储：把高频访问数据放在能快速取用的位置，借此提升应用响应速度、降低后端负载。Amazon ElastiCache 常用于存储 Web 应用的会话数据，以及加速实时分析数据的访问。

最后，存储生命周期策略能基于预定义规则自动在 S3 各存储类别之间迁移对象，兼顾成本与性能优化；而 AWS Backup 则是一项全托管的集中式备份服务，支持跨区域备份并可以设定保留和删除策略。

三、AI 与机器学习

在前两部分打好计算与数据基础之后，AWS 在 AI/ML 领域构建了一整套从”开箱即用”到”完全自定义”的服务体系。要理解这套体系，得先厘清两个常被混用的概念：人工智能（AI）是一个更宽泛的概念，指的是让机器模拟人类智能的各种方法，涵盖问题解决、语音识别、学习能力等多个方面；机器学习（ML）则是 AI 的一个子集，专注于让系统通过海量数据自主学习规律、推导结论，而不是靠人工写死的规则。AWS 把这块业务分成了四类：AI 服务、ML 服务、ML 框架与基础设施，以及一套通用的机器学习工作流程。

AI 服务

AWS 的 AI 类服务大多是预训练或自动训练好的模型，开发者不需要懂太多机器学习原理，直接调用接口就能把智能能力集成进自己的应用里。常见的几个包括：

  • Amazon Translate：多语言文本自动翻译。
  • Amazon Polly：文本转语音，输出接近真人的语音效果。
  • Amazon Lex：用于搭建聊天机器人一类的对话式交互界面，处理从开发到部署的整个流程。
  • Amazon Comprehend：文本分析工具，可以提取情感倾向、识别实体，或判断文本所使用的语言。
  • Amazon Forecast：基于历史数据自动生成时间序列预测。
  • Amazon CodeGuru：面向开发者的自动化代码审查工具，能给出提升代码质量的智能建议。
  • Amazon Rekognition：图像和视频识别服务，可以识别物体、提取情绪等信息。

这些服务的共同特点是”黑盒可用”——不需要关心背后的模型是怎么训练出来的，重点是解决业务问题。

ML 服务

如果 AI 服务提供的是现成的智能，那么 ML 服务面向的就是自己动手构建定制化模型的开发者和数据科学家。AWS 在这方面主要提供两个服务：

  • Amazon SageMaker：一个覆盖机器学习全生命周期的托管服务，集成了 Jupyter Notebook，支持快速训练和部署模型，可以用来做预测分析、计算机视觉、自然语言处理等各类应用。
  • Amazon CodeWhisperer：由机器学习驱动的代码审查工具，能自动化、简化整个代码审查流程，提升代码质量。

ML 框架

除了托管服务，AWS 也支持业界主流的开源机器学习框架运行在其基础设施之上，方便团队按需搭建可扩展、可定制的训练和部署流程。三个代表性框架是：

  • TensorFlow：谷歌开发的开源框架，支持模型的开发、部署与规模化扩展。
  • PyTorch：Meta 打造的深度学习框架，擅长处理基于计算图的动态执行场景。
  • MXNet：由 Apache 管理，专注于大规模、分布式的深度神经网络训练。

这一层的意义在于灵活性：企业不必完全依赖 AWS 的封装服务，也可以把已有的模型训练代码迁移到云端资源上继续跑。

一个典型的机器学习流水线长什么样？

把前面提到的计算、存储、数据库服务和 AI/ML 服务串起来，一个典型的 AWS ML 流水线大致是这样运作的：

  1. 数据存储：原始数据先存放在 S3 存储桶中，作为整个流程的数据源。
  2. 模型训练：SageMaker 直接从 S3 读取数据，完成模型的开发和训练。
  3. 部署上线：训练好的 SageMaker Notebook 被打包成容器，通过 EKS 推送到生产环境。
  4. 自动化再训练：当有新数据到来时，Lambda 会被触发，自动启动模型的重新训练和部署流程，让整个系统保持”自我更新”的能力。

这套流程很好地体现了 AWS 各服务模块之间的协作关系：S3 负责存数据，SageMaker 负责训练，EKS 负责稳定部署，Lambda 负责自动化触发——计算层、数据层与 AI 层在这里真正被打通成一条完整的工程闭环。

总结

把这三大模块串起来看，AWS 的核心服务体系其实遵循着一条清晰的逻辑链：

  • 计算层（EC2、ECS/EKS、Lambda/Fargate）负责”跑起来”——不管是传统虚拟机、容器化微服务，还是完全无服务器的事件驱动应用；
  • 数据与网络层（RDS/Aurora、DynamoDB/DocumentDB、MemoryDB、VPC、S3/EBS/EFS）负责”存得住、传得快、连得通”；
  • AI/ML 层（Translate、Rekognition、SageMaker、TensorFlow/PyTorch/MXNet）则是在前两层稳固的基础设施之上，把数据和算力转化为实际的智能应用——想要快速集成现成能力就用 AI 服务，想要自己训练定制模型就用 SageMaker，想要掌控底层框架就直接跑 TensorFlow/PyTorch/MXNet，想要搭建完整的生产级流水线，就组合使用 S3 + SageMaker + EKS + Lambda。

理解这条逻辑链，再去看 AWS 具体的产品名称和参数，会发现它们并不是孤立的功能点，而是彼此配合、服务于不同业务场景的一整套工具箱。这也正是 AWS 能够支撑起从初创公司到全球企业的各种复杂应用、并在 AI 时代持续领跑的原因所在。

AWS基础

AWS：云计算的核心概念全解析

本文基于 DataCamp《AWS Concepts》课程核心知识整理

一、什么是 AWS？

在当今数字化时代，云计算已经不再是”可选项”，而是企业 IT 基础设施的标配。而在众多云平台中，Amazon Web Services（AWS） 凭借其超过 200 种服务、覆盖全球的基础设施以及灵活的定价模式，牢牢占据市场领导地位。

无论你是初创公司还是世界 500 强企业，AWS 都能提供满足需求的工具：从存储数据、运行应用，到构建机器学习模型。

二、为什么选择云？

传统 IT 模式需要你提前购买服务器、机房、网络设备——这些都是巨大的前期资本投入（CapEx）。而 AWS 将这一切转变为按需付费的运营支出（OpEx）。

AWS 的核心价值可以从四个方面来解释：

1. 灵活性与敏捷性

无需提前规划容量。你可以在几分钟内启动服务器，也可以在业务缩减时立即释放资源，极大缩短了产品上市时间。

2. 成本优化

AWS 采用消费即付费的模式，只为你实际使用的资源买单，没有闲置成本，同时随着使用量的增加，还可以享受阶梯式折扣。

3. 弹性扩展

AWS 的架构天然支持水平扩展。无论你的用户量从 100 增长到 100 万，系统都能平滑应对，无需手动干预。

4. 全球覆盖

凭借遍布全球的区域（Region）和可用区（Availability Zone，AZ），AWS 让你的应用能够以极低的延迟服务全球用户，同时实现多地容灾。

三、AWS 的全球基础设施

理解 AWS 的全球架构，是用好 AWS 的第一步。

  • Region（区域）：AWS 在全球部署的独立地理区域，每个区域相互隔离，例如 us-east-1（美国东部）、ap-northeast-1（东京）。
  • Availability Zone（可用区）：每个区域内包含多个相互独立的可用区，由独立的电源、冷却和网络支撑。在多个 AZ 部署应用可实现高可用。
  • Edge Location（边缘节点）：用于 Amazon CloudFront 的内容分发，将内容缓存到离用户更近的地方，降低访问延迟。

选择 Region 的原则：合规要求 > 用户地理位置 > 服务可用性 > 成本。

四、AWS 的三种部署模式

根据业务需求，你可以选择不同的云部署模式：

模式 说明 适用场景
公有云（Public Cloud） 完全托管于 AWS 初创公司、快速迭代的互联网产品
私有云（Private Cloud） 企业自建或专属云环境 金融、医疗等强合规行业
混合云（Hybrid Cloud） 公有云 + 私有数据中心结合 有遗留系统且需要逐步迁云的企业

五、AWS 核心服务详解

AWS 的服务体系庞大，但入门阶段只需掌握三大支柱：计算、存储、数据库。

🖥️ 计算服务

Amazon EC2（Elastic Compute Cloud）

EC2 是 AWS 的虚拟机服务，提供可调整大小的云端计算资源。你可以选择不同的实例类型来匹配你的工作负载：

  • 通用型（如 t3.micro）：适合轻量应用和开发测试
  • 计算优化型（如 c6i）：适合高性能 Web 服务器、批处理
  • 内存优化型（如 r6g）：适合大型数据库、内存缓存

EC2 还支持：

  • 弹性负载均衡（ELB）：自动将流量分发到多个实例，避免单点故障
  • Auto Scaling：根据负载自动增减实例数量，做到真正的”按需使用”

AWS Lambda（无服务器计算）

如果你不想管理服务器，Lambda 是绝佳选择。你只需上传代码，AWS 自动处理所有基础设施——代码只在被触发时执行，只为实际运行时间付费，空闲时零成本。

场景：图片上传后自动触发压缩处理、API 请求的后端逻辑、定时任务。

存储服务

Amazon S3（Simple Storage Service）

S3 是 AWS 最具代表性的服务之一，提供对象存储，具备近乎无限的扩展能力和 99.999999999%（11 个 9）的数据持久性。

S3 根据访问频率提供不同的存储类别：

存储类别 适用场景 特点
S3 Standard 频繁访问的数据 高可用，低延迟
S3 Standard-IA 不频繁访问但需快速读取 存储成本低，读取费用较高
S3 Glacier 长期归档 极低成本，检索需要数小时
S3 Glacier Deep Archive 7年以上超长期归档 AWS 最低存储价格

Amazon EBS（Elastic Block Store）

如果 S3 是”U 盘”，那 EBS 就是”硬盘”。EBS 提供持久化的块存储，直接挂载到 EC2 实例，适合数据库、操作系统等需要低延迟 I/O 的场景。

数据库服务

Amazon RDS（Relational Database Service）

RDS 是托管的关系型数据库服务，支持 MySQL、PostgreSQL、Oracle、SQL Server 等主流引擎。AWS 负责底层的备份、打补丁、故障转移，你只需关注数据本身。

Amazon DynamoDB（NoSQL 数据库）

DynamoDB 是 AWS 的全托管 NoSQL 数据库，专为需要毫秒级延迟和超高并发的场景设计。无需预设 Schema，数据以键值对或文档形式存储，天然支持水平扩展。

何时选 RDS，何时选 DynamoDB？

  • 数据有复杂关系、需要 JOIN 查询 → RDS
  • 海量数据、高并发读写、灵活 Schema → DynamoDB

六、AWS 安全基础：共担责任模型

AWS 的安全体系建立在共担责任模型（Shared Responsibility Model） 之上：

简单记忆：AWS 负责云本身的安全，你负责云中资源的安全。

核心安全工具：

  • IAM（Identity and Access Management）：管理用户权限，坚守”最小权限原则”
  • VPC（Virtual Private Cloud）：在 AWS 内创建隔离的虚拟网络
  • CloudTrail：记录所有 API 调用日志，用于审计和合规

七、总结：AWS 知识

AWS 的服务生态十分庞大，但万变不离其宗——掌握计算、存储、数据库这三大核心，再逐步延伸到网络、安全、AI/ML 等领域，是最稳健的学习路径。

云计算的学习，最终还是要动手。理论只是起点，实践才是真正的加速器。

用 Hugging Face smolagents 打造智能 AI Agent

前言

AI Agent（AI 代理）正在改变我们与软件互动的方式。过去，我们给 LLM 一个问题，它回答；现在，Agent 能够搜索数据、推理、执行代码，甚至主动完成复杂任务。本篇博客整理 smolagents 框架的四大核心主题并学习多代理系统的设计

一、Introduction to Hugging Face smolagents

具体网址：Hugging Face Hub 文档

什么是 smolagents？

smolagents 是 Hugging Face 开发的轻量级 Python 框架，专为构建能够推理与行动的 AI Agent 而设计。它的核心理念是让 LLM 不只是”回答问题”，而是能够生成并执行 Python 代码来完成任务。

两种核心 Agent 类型

类型 说明 行动方式
CodeAgent smolagents 的主要 Agent 类型 生成并执行 Python 代码
ToolCallingAgent 第二种 Agent 类型 输出 JSON/文本格式，由系统解析后执行

CodeAgent 的优势在于它直接输出可执行的代码，逻辑更灵活、更强大；ToolCallingAgent 则更适合需要严格结构化输出的场景。

Tools（工具）：Agent 的行动工具

Tool是 Agent 能够调用的函数，是 Agent 的基本组成。smolagents 提供三种方式定义工具：

  1. 内置工具箱：如 DuckDuckGoSearchTool、VisitWebpageTool 等DuckDuckGoSearchTool：调用 DuckDuckGo 搜索引擎，帮 Agent 上网搜东西。相当于 Agent 的”百度一下”，不用 API Key，免费用
    VisitWebpageTool：打开一个网页，把里面的文字内容抓回来。搜到结果后点进去看具体内容，相当于 Agent 的”打开网页看一眼”
  2. @tool 装饰器：把一般函数变成 Agent 可调用的工具
  3. 继承 Tool 类：更完整的自定义工具实现

工具也可以分享到 Hugging Face Hub，或加载社区贡献的工具，形成开放的工具生态系统。

为什么选择 smolagents？

  • 轻量：核心逻辑精简，容易理解与修改
  • 与模型无关：支持 HF Inference、OpenAI、Ollama、vLLM 等多种后端，一行切换
  • 安全执行：代码可以在 Docker、E2B、WebAssembly sandbox 沙箱中隔离执行
  • 生态完整：深度整合 Hugging Face Hub，工具与模型唾手可得

二、Agenti RAG and Multi-Step Agents

传统的 RAG 限制

传统 RAG 的流程是：一次查询 → 一次检索 → 生成答案。这在面对复杂问题时容易出现”检索不够精准”或”信息不足”的困境，因为它无法根据中间结果动态调整搜索策略。

Agent RAG：让 Agent 主动检索

Agentic RAG 赋予 Agent 自主决策的能力：

  • 自主重构查询：根据问题语义，自动生成更精确的搜索词
  • 迭代式检索：分多步骤从不同来源获取信息
  • 批判性评估：自动判断检索结果是否足够，决定是否再次搜索
  • 多来源整合：同时结合网络搜索与本地知识库

规划间隔（Planning Intervals）

在多步骤任务中，可以设定让 Agent 定期”停下来想一想”——评估目前进度、调整接下来的行动策略，避免一直盲目执行而偏离目标。

回溯机制(Callbacks)：实时监控 Agent 行为

通过 Callback 机制，可以在 Agent 执行的每个步骤插入自定义逻辑，用于：

  • 实时追踪执行状态
  • 记录 Token 使用量与延迟
  • 在特定条件下中断或修改行为

Stateful Tools（有状态工具）

有别于一般无状态函数，Stateful Tool 能在多步骤任务中维持内部状态，例如记住上一步的检索结果，让后续步骤可以接续使用，大幅提升复杂任务的效率。

三、Multi-Agent Systems

为什么需要多代理系统？

单一 Agent 处理复杂任务时能力有限，以及 Context 窗口有限。多代理系统通过分工合作解决这个问题：把复杂任务拆分给专业 Agent，各司其职，再由 Manager Agent 协调整合。

架构设计：Manager(管理) + Specialist(专家)

Manager Agent 负责拆解任务、指派子任务给各专业 Agent，并整合最终结果。

典型的多代理 RAG 系统

一个完整的多代理 RAG 系统可能包含：

  • Web Agent：负责搜索网络最新信息
  • Retriever Agent：查询本地知识库或向量数据库
  • Image Generation Agent：按需求生成图像
  • Manager Agent：整合所有子 Agent 的输出

这种架构适合需要跨领域知识整合的复杂任务。

四、Memory and Validation

Memory：让 Agent 记住对话的上下文

没有记忆的 Agent 每次对话都是”从零开始”，无法处理追问或多轮任务。smolagents 的记忆系统让 Agent 能够：

  • 保留对话历史，自然处理追问
  • 记住已完成的步骤，避免重复工作
  • 根据过往互动调整策略

Memory 以步骤形式序列化存储，包含时间戳与 Token 使用量等元数据，方便后续分析。

执行追踪（Execution Traces）

除了记忆，smolagents 还提供详细的执行追踪：

  • 推理步骤记录：完整保留 Agent 每一步的思考过程
  • Debug 辅助：当 Agent 行为异常时，可以逐步回放推理过程找出问题
  • 性能分析：了解哪些步骤耗时、哪些工具调用最频繁

Validation（输出验证）

Agent 的输出不一定永远正确，验证机制是确保可靠性的关键环节：

常见验证方法：

  1. 结果相关性验证：确认检索到的信息确实回答了问题
  2. 格式验证：确保输出符合预期的数据结构
  3. 事实一致性检查：交叉比对多个来源的信息
  4. Fallback 机制：当主要方法失败时，启动备用策略

错误恢复：

smolagents 内置错误日志与重试机制，让 Agent 在遇到工具调用失败或结果不佳时，能自动尝试替代方案，而不是直接中断任务。

总结：smolagents 的核心设计哲学

主题 核心概念
基础框架 CodeAgent 以 Python 代码为行动语言，Tool 是行为积木
Agentic RAG 迭代式、多步骤的智能检索，取代一次性的静态查询
多代理系统 Manager 协调 Specialist，分工合作处理复杂工作流
记忆与验证 跨轮次记忆 + 执行追踪 + 验证策略，确保可靠输出

smolagents 的设计是框架本身保持轻量，让开发者能够完全理解其运作原理，同时通过工具生态与多代理协作，支撑起现实中的复杂应用场景。

无论是自动化数据的工作流还是智能文档问答系统，或者跨领域的研究助理，smolagents 都可以提供一个清晰、灵活、可扩展的起点。

Session

Session 是服务端存的数据，用来记住”这个用户是谁、登录了没有”。例如：

特点：

  • 存在服务器端（Flask 默认加密存在 Cookie 里，也可以存 Redis/数据库）

Cookie + Session 的配合流程：

  1. 用户输入密码登录
  2. 服务器验证通过 → 创建 Session（存用户信息）→ 返回一个 Session ID
  3. 浏览器把 Session ID 存到 Cookie 里
  4. 之后每次请求，浏览器自动在 Cookie 里带上 Session ID
  5. 服务器根据 Session ID 查到 Session 数据 → 知道是谁在操作

Redis

Redis 是一个内存数据库，数据存在内存里而不是硬盘上，所以读写极快。

Session 的存储方式之一就是 Redis：

存储方式 特点
Flask 默认（加密 Cookie） 简单，但数据量受限
Redis 快、支持分布式、服务器重启数据不丢
SQLite/MySQL 持久化，但比 Redis 慢

简单记住：Cookie 是浏览器存的通行证，Session 是服务器存的用户档案，Redis 是存放这些档案的高速柜子。
