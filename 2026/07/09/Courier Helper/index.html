Courier Helper

从零构建一个快递助手 App：Flutter + ML Kit + 微信监听实战

背景

做快递配送的朋友每天要处理大量地址信息：客户微信发来地址 → 手动录入快递系统 → 逐条下单。这个流程极其低效——先要看清每条地址，再切到快递 App 逐字输入，一条地址至少花 30 秒，一天上百单就是近一小时纯打字。

我花了一周时间，用 Flutter 做了一个 快递助手，核心目标：最小化手动输入，最大化自动化。从收到地址到完成下单，全程不超过 3 次点击。

本文记录完整的技术选型、架构设计和踩坑过程。

技术栈

层级 技术
UI 框架 Flutter 3.44（Dart）
数据库 SQLite（sqflite）
图片 OCR Google ML Kit Chinese Text Recognition
通知监听 Android NotificationListenerService
文件导入 Android Intent + 原生文件读取
状态管理 Provider + setState

项目结构

核心功能实现

1. 地址智能解析

这是整个 App 的核心——用户粘贴一段文字，自动拆分成姓名、电话、地址三个字段。

设计决策：第一版没有用 NLP 或大模型，纯正则。原因是快递地址格式极其固定——一定是”姓名 + 手机号 + 地址”的排列。用正则不仅快（毫秒级），而且离线可用、零依赖。

地址关键词过滤是关键优化——它让系统能区分”张三 13800138000 北京市朝阳区”和”充值 13800138000 元话费”，后者不含地址关键词，会被自动过滤。

2. 一键复制与格式化

传统工作流：看地址 → 切输入法 → 打字。改成一键复制后：

快递员点一下 → 三条信息全部进剪贴板 → 切到快递 App 粘贴 → 下单。从 30 秒降到 3 秒。

3. 微信通知监听（Android Native）

这是最”黑科技”的功能：别人微信发来地址，App 自动识别并导入，用户无需操作。

4. 图片 OCR 识别

用户收到的是截图怎么办？Google ML Kit 解决。

Flutter 拿到识别文字后，复用 AddressParser.parseMultiLine() 提取地址。

选型考量：ML Kit 的优点是完全离线运行、支持中文识别、精准度高。缺点是模型约 40MB，导致 APK 体积较大（78MB）。Tesseract OCR 更轻量但中文识别率不佳，百度 OCR API 需要网络且收费。离线中文 OCR 场景下，ML Kit 是目前最优解。

5. 三步去重机制

快递场景下，同一地址一天重复下单是常见错误。App 做了三层防护：

  1. 手动添加 → 弹窗警告”今天已下过此单”，可选择继续或取消
  2. 批量导入 → 自动标记重复项为橙色，跳过不导入
  3. 微信自动导入 → 去重检测仍然生效，但自动模式不拦截

去重算法是字符串级别的标准化：去除空格 → 转小写 → 去掉”省””市”后缀 → 对比。简单但有效，对快递地址这个场景足够。

踩坑记录

坑 1：Kotlin Gradle Plugin (KGP) 冲突

现象：项目中引入 fluttertoast、share_plus、file_picker 等插件后编译失败，报错：

根因：Flutter 3.44 内置了 Kotlin 编译器（Built-in Kotlin），而旧版第三方插件自带了一套 Kotlin Gradle Plugin。两套 KGP 同时运行，缓存冲突。

解决方案：逐个替换掉有 KGP 问题的插件：

原插件 问题 替代方案
fluttertoast KGP 冲突 Flutter 内置 SnackBar
share_plus KGP 冲突 原生 Intent + FileProvider
file_picker KGP 冲突 原生 Intent.ACTION_OPEN_DOCUMENT

原生实现的好处不仅是避开 KGP 问题——还减少了依赖数量，APK 更小，应用更可控。

坑 2：国内网络环境

在无代理的 Windows 环境下，Flutter SDK 安装、pub 依赖下载、Android SDK 组件下载、Gradle 依赖下载全部失败。

解决方案：

  • Flutter SDK 从 flutter.cn 直链下载 zip
  • 设置 PUB_HOSTED_URL 和 FLUTTER_STORAGE_BASE_URL 镜像
  • Android Studio 从 developer.android.google.cn 下载
  • maven.google.com 超时依赖已有的离线缓存

坑 3：微信通知的多样性

微信的通知文本格式不统一——单人聊天、群聊、公众号、服务通知的通知结构完全不同。

解决方案：

  • 过滤 title 包含”公众号””微信团队”的通知
  • 过滤 text 包含”条新消息”的群聊通知
  • 地址关键词二次校验，确保只导入真正的地址

构建与发布

当前版本 78MB（其中 ML Kit 中文模型占 40MB）。无需服务器，数据库存本地，数据安全。

一周时间，一行后端代码没写，做出了一个能真正提高快递员效率的工具。Flutter 在跨平台 UI 上的生产力 + Android 原生 API 的能力，让”个人开发者做实用 App”这件事变得非常可行。
