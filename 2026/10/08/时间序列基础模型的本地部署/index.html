2.2 中途出现过的错误

因为前面多次中断 Conda，还遇到过：

这三个错误的含义分别是：

  • **CondaError: KeyboardInterrupt**：通常表示 Conda 正在执行时被手动中断了
  • **free(): corrupted unsorted chunks**：表示某个 Conda 相关的原生库在退出或处理中发现内存状态不对
  • **Aborted (core dumped)**：表示 Linux 发现进程出现了严重的底层错误，于是强制终止了这个进程；core dumped 的意思是系统可能生成了一个 core dump，用来保存程序崩溃时的内存状态，方便底层调试

这个过程给我的第一个结论是：

Conda 卡在 metadata 阶段时，不要第一反应就反复 Ctrl+C。先检查 channel、repodata 大小以及是否真的需要 conda-forge。

对于这种部署环境，首要目的是跑通和稳定，而不是 channel 越多越好。

8. 一个很常见的坑：422 Unprocessable Entity

公网测试 /predict 时，曾经出现过一次 422，之后修改请求格式又正常返回 200。

这个错误很容易被当成”模型报错”或者”GPU 挂了”。但在 FastAPI 中，422 很常见的含义是：

请求已经到达 FastAPI，但 JSON body 没有通过 Pydantic / 请求 schema 校验。

比如接口期待：

如果字段名、类型或者 JSON 结构不匹配，就可能直接在模型执行之前返回 422。

所以看到 POST /predict → 422，第一件事应该检查：

  • Request body
  • 字段名
  • 字段类型
  • JSON 格式

而不是先去重启 GPU。

9. p10、p50、p90 和 mean 是什么？

Chronos 返回的并不只是一个未来值，而是预测分布的摘要。假设某个未来时间点得到：

可以这样理解：

  • **p10**：预测分布的 10% 分位数，大约 10% 的预测概率质量位于它以下
  • **p50**：50% 分位数，也就是 median / 中位数预测，它经常被直接用作一个 robust 的点预测
  • **p90**：预测分布的 90% 分位数，大约 90% 的预测概率质量位于它以下

因此 [p10, p90] 可以理解为模型预测分布的中央 80% 区间。

注意：这描述的是模型自身的预测分布，不等于”真实世界一定有严格 80% 的覆盖率”；是否校准准确，需要用真实数据验证。

mean 则是预测分布的平均值。如果只需要一个 point forecast，可以优先考虑 p50 或者 mean，但要注意：

只有分布比较对称时，两者才可能接近。今天的接口结果中它们可能恰好相同，但统计意义上不能默认二者永远相等。

12. 现在的服务还不能直接投入实际使用

模型现在已经可以长期运行了，但如果直接把 http://<YOUR_SERVER_IP>:8000 长期暴露在公网，风险很大。因为任何知道 IP 和端口的人，都可能调用 GPU。

而 GPU API 和普通 CRUD API 最大的区别是：

一次请求可能对应真实、昂贵且有限的 GPU 计算资源。

因此保护 GPU也是重要的手段。

15. GPU API 一定要做 Rate Limit 和并发控制

普通 Web 服务扛不住攻击时，可能主要表现为 CPU、连接数或数据库压力。GPU inference 服务还有一个更直接的问题：

别人只需要一个循环，就可能把 T4 长时间占满。所以至少需要两类限制。

16. 限制输入

现在的接口非常简单：

但正式开放之后，不能假设客户端一定会传合理的输入，所以一定要加类似的约束：

  • values 最短：2
  • values 最长：2048
  • prediction_length：1 ~ 64
  • 禁止 NaN
  • 禁止 Inf
  • 限制 JSON body 大小

原因很简单：超长的 context、超长的 horizon、异常数字、超大的 body，都可能造成额外 CPU、RAM、GPU 压力。

这不是模型的问题，而是 API 的设计问题。

17. HTTP 的状态码

API 对外开放时，需要明确每个错误状态码代表什么：

状态码 含义
400 输入非法
401 API Key 无效
422 请求 schema 校验失败
429 调用过于频繁
500 模型或内部异常
503 GPU 忙 / 暂时不可用

这样客户端看到错误时，可以直接判断问题属于哪一类，而不是所有异常都只返回 500。

18. 总结

1. Conda 卡住不一定是”没网”

可能只是 repodata 太大。先看 channel，再看 metadata 大小。

2. GPU 驱动正常，不代表 PyTorch CUDA 就一定正常

先检查 torch.cuda.is_available()。

3. 大 wheel 的下载源非常重要

900 MB 的包在 60 KB/s 和几十 MB/s 下，要尽早决定更换国内镜像源。

4. 422 通常先检查请求 schema

不要看到预测失败就第一时间重启模型和 GPU。

5. 0.0.0.0 解决的是”监听外部网卡”

它不等于端口一定能从公网访问，公网仍然要考虑服务器网络和安全策略。

6. “SSH 断了还能跑”与”服务器重启还能跑”不是一回事

长期服务必须验证 reboot 后是否自动恢复。

7. GPU API 的关键不是只让它”能访问”

而是：

  • 别人能调用多少次
  • 一个异常请求会不会让 GPU 死机
  • 服务崩了会不会自动重启
  • 出了问题能不能知道问题的来源
